## 0. Резюме и вердикт по реализуемости

### 0.1 Короткий ответ на главный вопрос

> «Как найти нужный трек в торренте с полной дискографией, не скачивая торрент целиком?»

**Реализуемо, и задача сводится к трём независимым механизмам, каждый из которых покрывает свой класс раздач:**

| Класс раздачи | Доля на практике | Механизм поиска трека | Что качается |
|---|---|---|---|
| **Мультифайловый торрент** (папка с отдельными файлами треков) | ~80–90 % музыкальных раздач на rutracker (в названии обычно помечено `FLAC (tracks)`) | Список файлов **уже содержится в `.torrent`** (`info.files`). Каждый файл = отдельный трек, у него есть точный byte-offset в «склеенном» потоке | Только piece'ы, перекрывающие нужный файл (обычно 3–30 МБ вместо 500 МБ) |
| **Однофайловый торрент** (один `.flac`/`.mp3`/`.rar`/`.zip` на всю дискографию) | ~10–20 % | **Свой индекс- sniffер по формату**: читаем только первые 1–2 МБ (или хвост) и строим карту треков по заголовкам контейнера: `ID3v2`/MPEG-фреймы (+Xing/VBRI), `fLaC` (STREAMINFO/VORBIS_COMMENT/CUESHEET), `PK` (ZIP: EOCD+Central Directory), `Rar!` (RAR4/RAR5 non-solid) | Только нужные диапазоны (в ZIP/RAR — точные байты записи) либо «режим непрерывного стрима» с произвольным доступом по piece'ам |
| **Rar solid / неиндексируемый формат** | единицы | Индекс недоступен без полных данных | Fallback: обычное скачивание торрента с предупреждением |

**Ключевой технический факт, который всё упрощает:** в BitTorrent *piece* — единица передачи, и **piece можно запросить у пира произвольно, без скачивания предыдущих**. Ограничение «скачать можно только подряд» существует только в UI обычных клиентов, а не в протоколе. Собственный piece-picker (или `File.SetPriority(0)` / `Piece.SetPriority()` в `anacrolix/torrent`) снимает это ограничение полностью.

**Второй ключевой факт:** сам rutracker отдаёт список внутренних файлов торрента через отдельную страницу (`viewtorrent.php`), то есть «список треков» можно получить **без скачивания .torrent и без скачивания данных** — из метаданных темы. Это же служит источником треклиста (если автор его не добавил).

**Итог по SSD:** вместо «скачать 500 МБ → послушать 4 минуты → удалить» приложение скачивает **только нужные piece'ы**. Типичный трек (5 МБ FLAC) = ~6 МБ трафика вместо 500 МБ. Износ SSD падает примерно в 80–100 раз, а не «в 10 раз». Плюс режим «RAM-only» (вообще без записи на диск).

Требования и деградация описаны в §6.2 и §13.

## 1. Контекст, цель, границы

### 1.1 Контекст

В стране пользователя музыка подвергается регулированию: легальные сервисы ограничивают каталог, часть сервисов заблокирована. Rutracker содержит большой архив раздач музыки, значительная часть которого — lossless (FLAC/ALAC/APE/WavPack) и полные дискографии, недоступные в стриминговых сервисах. Формат раздач (полная дискография одним торрентом) делает «качать, чтобы послушать один трек» нерациональным.

### 1.2 Цель

Десктопное приложение, которое:

- даёт **каталог** музыкальных разделов rutracker с подбором исполнителей/альбомов/треков;
- **проигрывает трек потоково**, скачивая только нужные байты торрента;
- **докачивает** выбранный трек/альбом/дискографию целиком по явному запросу;
- **приоритизирует lossless**;
- **минимизирует запись на диск** (режим RAM-only по умолчанию для стриминга).

### 1.3 Что НЕ входит в объём (out of scope)

- Обход блокировок на уровне DPI/ТСПУ (приложение умеет работать **через** SOCKS5/HTTP-прокси/VPN, но само не реализует и не встраивает обход DPI).
- Торрент-клиент общего назначения (нет поддержки magnet из браузера, нет раздачи всего подряд, нет «скачать всё» без явного действия).
- Хранилище музыкальной библиотеки в стиле Plex/Local Music Server (кроме локального кэша скачанного).
- Мобильные клиенты, веб-версия.
- Интеграция с DRM-сервисами (Qobuz/Apple/Amazon/Spotify) — только опционально через внешние API-адаптеры (§23).

### 1.4 Границы допустимого использования

Приложение — это **клиент**: оно не содержит и не распространяет аудиофайлы, а лишь соединяет пользователя с пирами. Ответственность за правомерность использования контента, соблюдение правил сайта (в т.ч. поддержание рейтинга раздачи) и законодательства своей страны остаётся на пользователе. В ТЗ закладываются технические меры, снижающие риски: отсутствие телеметрии, шифрование учётных данных, «инкогнито»-режим, отсутствие автообновления содержимого кэша.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Раздача** (релиз, topic) | Тема на форуме rutracker с одним или несколькими торрентами |
| **Торрент** (`.torrent`) | Metainfo-файл: описание раскладки, размеров, piece'ов и хешей |
| **Piece** | Единица передачи и проверки целостности, обычно 256 КБ – 2 МБ |
| **Metainfo / `info` dict** | Словарь bencode с `name`, `piece length`, `pieces`, `files`/`length` |
| **Мультифайловый торрент** | `info.files` — список; содержимое склеивается в один поток, у каждого файла свой offset |
| **Однофайловый торрент** | `info.length` — один файл на всю дискографию |
| **Padding file (BEP 47)** | Служебный файл-«распорка», перекрывает границы piece'ов; качать не нужно |
| **BEP 52 (v2)** | Merkle-дерево, per-file целостность; поддерживается в v2/hybrid торрентах |
| **Announce** | Обращение к трекеру: отдаём `info_hash` + IP/порт, получаем список пиров |
| **Passkey** | Секретный ключ пользователя в URL трекера (на rutracker — внутри `announce`/магнита) |
| **Ratio** | Отношение отданного к скачанному; на rutracker влияет на права и репутацию |
| **TTFA** | Time To First Audio — время от клика по треку до первого звука |
| **Sniffing** | Определение формата/структуры файла по сигнатуре и заголовкам |
| **Resync** | Поиск валидного кадра/фрейма в середине потока (после «прыжка» на произвольный piece) |
| **CUE sheet** | Текстовый файл `.cue` с точными смещениями треков (часто лежит рядом с FLAC в раздаче) |
| **Lossless** | FLAC, ALAC, APE, WavPack, WAV, DSD, а также 24/192 bit варианты |

### 3.3 Ключевой поток данных: «пользователь нажал ▶ на трек»

```
UI: click(track)
  └─> Playback Orchestrator.Resolve(trackID)
        ├─ Catalog: найти release/torrent (topic_id, infohash)
        ├─ Rutracker: получить .torrent (dl.php) → metainfo
        ├─ MediaIndex: filePath → byteRange → pieceRange
        ├─ Torrent Engine: AddTorrent(info) + SetPriority(нужный файл) + DownloadPieces(p0..p1)
        │     ├─ Announce (с passkey) → пиры
        │     ├─ Handshake → piece request → проверка хеша → запись в piece store
        │     └─ события: pieceReady / bufferLevel
        └─ Audio: fileReader(seek=offset) → decoder → resampler → device
              └─ UI: TTFA, буфер %, битрейт, кнопка «докачать»
```

## 5. Ключевой технический вопрос: как найти трек, не скачивая торрент

Это самый важный раздел ТЗ. Ниже — полный разбор с алгоритмами.

### 5.1 Уровень 0: что уже лежит в `.torrent`

Metainfo мультифайлового торрента:

```
d8:announce…6:lengthi…4:list…d5:filesl
  d6:lengthi10485760  4:pathl9:AlbumFLAC6:01.flac  e
  d6:lengthi9823040   4:pathl9:AlbumFLAC6:02.flac  e
  …                                     (по файлу на трек)
  4:piece lengthi262144
  5:pieces0:…(SHA-1 × NumPieces)
```

Из этого **без единого байта аудио** известно:

- сколько всего файлов и как они названы (`01 - Title.flac`, `CD1/01 Title.flac`, …);
- точный byte-offset каждого файла в склеенном потоке (кумулятивная сумма `length`);
- `piece length` и число piece'ов;
- хеши piece'ов (для проверки целостности) и, для v2, Merkle-корень каждого файла.

**Вывод: для 80–90 % музыкальных раздач задача «найти трек» сводится к сопоставлению имён файлов с названиями треков — это чистая задача парсинга строк, а не скачивания данных.**

Дополнительный бонус: rutracker сам показывает этот список (`viewtorrent.php`), поэтому треклист известен ещё **до** скачивания `.torrent`.

### 5.2 Уровень 1: мультифайловый торрент — алгоритм

```
Вход: infohash, список trackID → (имя трека, альбом, длительность?)
Выход: TrackPlan{ fileIndex, byteStart, byteEnd, pieceStart, pieceEnd, extraBytes }

1. files := metainfo.Info.UpvertedFiles()        // с готовыми Offset
2. offset := 0
3. для каждого file: file.Offset = offset; offset += file.Length
4. candidates := файлы, чьё расширение — аудио (.flac .mp3 .m4a .ape .wv .ogg .wav .dsf .dff)
5. для каждого trackID:
     a. нормализовать: lower, ё→е, убрать пунктуацию, trim
     b. точное совпадение нормализованного имени файла (без расширения) → score 1.0
     c. иначе: совпадение по «ядру» (номер трека + название) → score 0.9
     d. иначе: fuzzy (Levenshtein/Jaro-Winkler + token-set-ratio) с отсечкой 0.75
     e. иначе: сравнить с треклистом из темы форума (см. §5.5) → score 0.85
     f. иначе: оставить неразрешённым, показать пользователю «не найдено»
6. pieceStart := byteStart / pieceLength
   pieceEnd   := (byteEnd - 1) / pieceLength
7. extraBytes := (pieceStart+1)*pieceLength - byteStart + byteEnd - pieceEnd*pieceLength
   // «лишние» байты, которые придётся скачать из-за выравнивания по piece'ам
```

**Типичные числа (проверено на логике):**

| Размер трека | piece length | piece'ов | Лишние байты | Доля от торрента |
|---|---|---|---|---|
| FLAC 5 МБ, трек №7 из 80 | 256 КБ | 20 | ≤ 0.5 МБ | ~1 % |
| FLAC 30 МБ (длинный трек) | 1 МБ | 30 | ≤ 2 МБ | ~1 % |
| MP3 10 МБ | 256 КБ | 40 | ≤ 0.5 МБ | ~1 % |

Т.е. **типичный трек = 1–2 % от размера раздачи**, а не 100 %.

### 5.3 Уровень 2: однофайловый торрент — sniffers по форматам

Цель: получить карту «трек → byte-range» **без скачивания всего файла**.

#### 5.3.1 Общий механизм: «прыжок» + resync

В BitTorrent можно запросить **любой** piece. Поэтому:

1. Скачиваем 1–2 первых piece'а (512 КБ – 2 МБ) — почти всегда достаточно, чтобы прочитать заголовок.
2. Определяем формат по сигнатуре.
3. Строим индекс (см. ниже). Если индекс требует данных в середине/конце файла — запрашиваем нужные piece'ы точечно (это 1–5 piece'ов, а не весь файл).
4. Если трек начинается не на границе piece'а — «прыгаем» на piece, содержащий нужный offset, и делаем **resync**: сканируем байты до валидной границы фрейма/фрейма FLAC.

#### 5.3.2 FLAC (`.flac`)

```
"fLaC" (4 байта) → блоки METADATA:
  STREAMINFO (тип 0): min/max blocksize, min/max framesize,
                       sample_rate(20 бит), channels(3), bits_per_sample(5),
                       total_samples(36 бит)  → duration = total_samples / sample_rate
  VORBIS_COMMENT (тип 4): ARTIST, ALBUM, TITLE, TRACKNUMBER, DISCNUMBER, …
  CUESHEET (тип 5): если есть — точные смещения треков (в samples)
  PICTURE (тип 6): обложка
```

- Если в раздаче есть отдельный `.cue` → **точный** треклист с sample-accurate смещениями (файл `.cue` лежит в мультифайловом торренте → его можно скачать целиком, он крошечный).
- Если `.cue` нет и CUESHEET нет → трек = весь файл; внутри файла границ нет (FLAC без cue-разметки — на практике редкость для альбомов).
- **Побочная выгода:** `STREAMINFO` даёт точный битрейт (lossless) → сразу виден «24/96» и т.п.

#### 5.3.3 MP3 (`.mp3`, один файл = несколько треков)

```
1. ID3v2: "ID3" + версия + флаги + syncsafe size → размер тега, пропускаем.
   (тег может содержать несколько песен — тогда границы треков известны точно)
2. Первый MPEG-фрейм:
   - Xing/Info (в site 32) → VBR: total frames, bytes, TOC (100 точек) → точная длительность и seek
   - VBRI (Fraunhofer, offset 32 после заголовка) → аналогично
   - иначе CBR: длительность = (размер − теги) × 8 / битрейт
3. Границы треков:
   - если в ID3v2 есть несколько треков (нестандарт, но встречается) → точные
   - если есть Xing TOC → приблизительные, по 100 точкам
   - иначе: границ нет; трек = весь файл, и мы НЕ МОЖЕМ выбрать отдельную песню
     → применяем «режим непрерывного стрима»: играем файл целиком как один трек
```

**Важный вывод:** склеенные MP3-дискографии (а это классика 2000-х) придётся слушать как один длинный трек. Это ограничение формата, а не протокола. Для FLAC-раздач (актуальные релизы) проблемы нет.

#### 5.3.4 ZIP (`.zip`)

```
EOCD (End of Central Directory) в хвосте: ищем с конца сигнатуру "PK\x05\x06" (до 64 КБ с конца)
  → смещение и размер Central Directory
Central Directory: список записей (имя, compressed size, CRC32, method, local header offset)
Local File Header по offset: "PK\x03\x04" + 30 байт → точное смещение данных записи
```

Итог: **точный byte-range для каждого трека внутри архива**, распаковка — `compress/flate`. Требует скачать: хвост (~1–64 КБ) + начало (central dir + local headers, обычно < 100 КБ) + сами записи нужного трека. Отлично подходит для «альбом в одном zip».

#### 5.3.5 RAR (`.rar`)

- **RAR4** (`Rar!\x1A\x07\x00`): заголовки блоков идут последовательно, данные файлов — между ними. Разбор: читаем блоки, для `FILE_HEAD` получаем `unpacked size`, `packed size`, `file name`, `highpos`; вычисляем смещение данных. Скачиваем только нужные куски (заголовки + данные нужного файла).
- **RAR5** (`Rar!\x1A\x07\x01\x00`): аналогично, формат заголовков другой, но принцип тот же.
- **Solid-архив** (`solid=1`): данные файлов сжаты *jointly* → **вытащить один файл без полной загрузки невозможно**. Честно помечаем такие раздачи и предлагаем обычное скачивание.

#### 5.3.6 Прочие

| Формат | Что делаем |
|---|---|
| OGG (`OggS`) | Разбор страниц Vorbis/Opus: заголовок содержит rate/channels; границы треков — по страницам с разными `serial`/granule |
| WAV (`RIFF…WAVE`) | Базовый заголовок: rate/bits/channels; границы треков — по `data`-чанкам (нужен полный заголовок) |
| M4A/MP4 (`ftyp`) | `moov`/`trak` атомы дают длительность и битрейт; треки — по главам `chpl`/`sidx` |
| APE/Monkey's (`MAC `) | заголовок APEv2 + `Descriptor` блок с total frames |
| WavPack (`wvp `) | блок `Metadata` с sample count |
| DSD (`.dsf`) | формат DSD chunked (DSDIFF) — заголовок + таблица размеров треков |

### 5.4 Уровень 3: треклист с сайта как внешний индекс

Даже если sniffer не дал границ (склеенный MP3, solid RAR), у нас есть **треклист автора раздачи**:

- Тело темы форума: в музыкальных раздачах автор обычно публикует таблицу «№ — Название — Длительность», иногда в BBCode или в тегах `{artist} {album} {track}`.
- Теги темы (`span.post-b`): «Исполнитель», «Альбом», «Год», «Жанр», «Формат», «Битрейт», «Длительность».
- Имя файла (часто по шаблону `{NN} - {Title}.{ext}`).

Сопоставление треклиста с физическими файлами даёт:
- **отображение** треков в UI (даже если играть нельзя);
- **выбор** нужного файла в мультифайловом торренте (это основной сценарий);
- для однофайловых склеенных MP3 — понимание, что отдельный трек недоступен (но треклист показываем).

### 5.5 Уровень 4: «общий» треклист раздачи → трек → файл (fuzzy)

Схема сопоставления (используется в 2 местах: треклист темы ↔ файлы торрента, и поиск по названию трека ↔ каталог):

```
normalize(s):
  lower(s); ё→е; replace(/[«»"'()\[\]]/g, " "); replace(/\.(flac|mp3|m4a|ape|wv|ogg|wav)$/i,"");
  replace(/^\s*\d{1,3}\s*[-._)]\s*/, "");           # убрать номер трека
  collapse whitespace; trim

score(a, b):
  if a == b: 1.0
  if tokenSetRatio(a,b) > 0.9: 0.95
  if levenshtein(a,b) normalized > 0.85: 0.9
  if a contains b (or vice versa) and len(b) >= 6: 0.8
  if jaroWinkler(a,b) > 0.88: 0.75
  else 0
```

Порог 0.75; при нескольких кандидатах выбираем лучший, при равенстве — помечаем как «неоднозначно» и просим пользователя.

### 5.6 Уровень 5: локальный кэш индекса

Индекс (файлы, треки, смещения) сохраняется в SQLite по ключу `infohash + piece_length + files_hash`. Повторное открытие той же раздачи — мгновенный треклист без sniff'а. Плюс: приложение может помнить «я уже знаю, где лежит трек X в раздаче Y» — это решает проблему и для однофайловых раздач после первого раза.

### 5.7 Сводка: что скачивается в разных сценариях

| Сценарий | Размер раздачи | Скачано до первого звука | Скачано за трек целиком |
|---|---|---|---|
| Мультифайл, FLAC, трек 5 МБ | 500 МБ | 0.5–2 МБ (1 piece + метаданные) | 5–6 МБ |
| Мультифайл, MP3, трек 8 МБ | 500 МБ | 0.25–1 МБ | 8–9 МБ |
| Однофайл FLAC + .cue | 500 МБ | 1–2 МБ (первые piece'ы) + .cue | весь файл (или диапазон по cue) |
| Однофайл MP3 со Xing | 300 МБ | 0.5 МБ | весь файл (границ нет) |
| Однофайл ZIP | 400 МБ | 64 КБ (хвост) + 100 КБ | диапазон записи трека |
| Solid RAR | 500 МБ | 2 МБ (заголовки) | **требуется полная загрузка** |

### 5.8 Что делать, если трек найти нельзя

Приложение **не врёт** и не «играет тишину»:

1. Показывает: «Раздача — один склеенный MP3 без разметки; отдельные треки недоступны. Доступен непрерывный поток (44 мин).»
2. Предлагает альтернативу: «Найти альбом в другом качестве/раздаче» (поиск по треклисту среди lossless-раздач).
3. Предлагает fallback-источник (§23).

## 6. Модуль Rutracker Client

### 6.1 Транспортный слой

Три уровня деградации (автоматический failover):

```
Transport
 ├─ T1: Direct HTTP  (net/http + uTLS-подобный fingerprint при необходимости)
 │      cookies: bb_session (+ cf_clearance, если есть)
 │      заголовки: User-Agent Chrome, Accept, Accept-Language: ru-RU, Referer
 │      кодировка ответа: windows-1251 → UTF-8 (golang.org/x/net/html/charset)
 ├─ T2: Browser Transport (headless Chromium через go-rod)
 │      используется: (а) при 403 + CF-challenge, (б) для логина, (в) как источник cookie
 │      cookie-jar шарится с T1
 └─ T3: Manual (пользователь вставляет cookie из своего браузера; QR/парсер расширения)
```

Правила:
- Все запросы идут через настроенный прокси (если задан) — см. §13.
- Ротация зеркал: `rutracker.org` → `rutracker.net` → `rutracker.nl`; домен из magnet/`.torrent` (например `t-ru.org`) — только для announce, не для HTML.
- Межзапросные паузы и jitter, чтобы не выглядеть роботом (1–3 с, ±40 %).
- Кэш ответов в SQLite: тема (6 ч), список раздач раздела (15 мин), дерево разделов (7 суток).

### 6.2 Авторизация

```
POST /forum/login.php
  formhash = из GET /forum/login.php   (скрытое поле)
  username, password, autologin=on, login=«Вход»
→ Set-Cookie: bb_session=…; phpbb3_… 
```

Требования:
- Пароль не сохраняется; сохраняется только `bb_session` (шифруется, см. §14).
- Проверка слинка: запрос `GET /forum/index.php` → наличие маркеров «Выход»/«Мой профиль» в DOM.
- Автоматический повтор логина при `Session expired` (код 403 + редирект на login.php).
- «Не запоминать» режим: cookie живёт только в памяти процесса.

### 7.1 Выбор технологии

| Требование | API в `anacrolix/torrent` |

Альтернативы и их минусы:

| Альтернатива | Минусы для нашей задачи |
|---|---|
| `libtorrent` (C++/CGo) | CGo, тяжёлая сборка, но: эталонная реализация, стабильный piece-picker |
| Свой клиент с нуля | Полный контроль, но 3–6 месяцев; BEP 9/10/52, µTP, NAT-PMP — лишняя работа |

**Решение:** Phase 0 проверяет поведение `anacrolix/torrent` в части piece-priorities и streaming; если выявятся ограничения (например, нельзя «качать только файл X» без загрузки соседних piece'ов) — расширяем собственный piece-picker поверх публичного API библиотеки либо переходим на libtorrent (адаптерный слой `internal/torrent` изолирует зависимость).

### 7.2 Piece-picker (выбор нужных piece'ов)

```
want[piece] ∈ {0,1}  // белый список
have[piece] ∈ {0,1}

приоритеты:
  1. piece'ы из активного трека (текущий + следующий в очереди)  → PiecePriority.High
  2. piece'ы «превью» (первый piece файла)                       → PiecePriority.Normal
  3. остальные                                                 → PiecePriority.None / File.SetPriority(0)

выбор среди want ∧ ¬have:
  - rarest-first: сортировка по числу пиров, у которых piece есть (из bitfield'ов)
  - при < 10 оставшихся piece'ов — endgame: отдаём 2–3 peer'ам одновременно
  - round-robin по peer'ам, без starvation
```

Ограничение: piece'ы, перекрывающие границу «нужного файла» и «ненужного файла», всё равно скачиваются целиком (выравнивание). Отсюда «лишние байты» из §5.2.

### 7.3 Announce

```
GET {announce}?info_hash={20 raw bytes, url-encoded}
    &peer_id=-{client 8 chars}{12 random}
    &port={port}
    &uploaded=…&downloaded=…&left=…
    &compact=1&numwant=…&event=started|stopped
    &key=…&supportcrypto=1
```

- Announce-URL берём **из магнита/`.torrent`** (`announce`, `announce-list`), а не хардкодим: rutracker периодически меняет announce-домены (в разведке — `bt2.t-ru.org/ann`).
- Ответ: bencode `{interval, min interval, peers (compact|list), peers6}`.
- Переотправка `stopped` при выходе — критично для ratio/статистики трекера.
- **Риск:** announce-хост за Cloudflare (§0.2, ответ 403 на тестовом GET). Проверяется в Phase 0. Митигации: (а) UA как у qBittorrent/Transmission; (б) announce по HTTPS, если сервер поддерживает; (в) если CF режет — приложение сообщает об этом и предлагает альтернативный путь (см. §7.6).

### 7.4 Peer-соединения

- TCP-only (µTP выключен).
- Handshake: `pstr` (BEP 3) + расширения: BEP 9 (PEX), BEP 10 (UTP — выкл), BEP 20 (расширения), BEP 11 (LT), BEP 6 (DHT).
- Расширения PEX/DHT объявлены, но не используются (приватный трекер) — чтобы не мешать.
- Таймауты: connect 10 с, handshake 10 с, keepalive 120 с, request timeout 30 с.
- Одновременных peer'ов: 20–50 (по умолчанию 30) — с учётом того, что нам нужны лишь несколько piece'ов.
- Исходящие соединения — через SOCKS5/HTTP-прокси, если настроен.

### 7.5 Хранение piece'ов

```
PieceStore (in-memory, LRU) → при переполнении вытесняет ненужные piece'ы
    ↓ (для режима «скачать») 
FileCache (sparse preallocated file на раздачу) + индекс piece→offset
```

- Один **sparse** файл на раздачу: `data/<infohash>.dat` размером = total length (создаётся один раз, растёт через `SetLength`; на NTFS/ext4 реальные блоки выделяются только под записанные куски).
- Запись — по offset'у piece'а, без создания/удаления временных файлов → минимизация износа SSD и inode churn.
- Проверка piece'а: SHA-1 (v1) / Merkle (v2) из `metainfo`; несовпавший piece — в blacklist, перезапрос у другого peer'а.

### 7.6 Сценарий «0 сидеров»

| Симптом | Реакция |
|---|---|
| Announce вернул 0 peer'ов | Показать «нет источников», предложить: (1) подождать N минут (повторный announce), (2) «проверить и завершить» позже, (3) fallback-источник (§23) |
| Пиры есть, но все без нужных piece'ов | Пересчитать piece-план (сузить до 1 piece'а «превью»), показать прогресс |
| CF режет announce | Показать диагностику (код, CF-RAY), предложить проверить прокси/сеть |

## 8. Модуль Media Index (детально)

### 8.1 Интерфейс

```go
// internal/mediaindex
type TrackPlan struct {
    TrackID      string        // внутренний id трека
    FilePath     string        // путь внутри торрента ("Album/03 - Song.flac")
    ByteStart    int64         // смещение в склеенном потоке
    ByteEnd      int64
    PieceStart   int
    PieceEnd     int
    ExtraBytes   int64         // лишние байты из-за выравнивания
    Codec        string        // flac|mp3|m4a|ape|wv|ogg|wav|zip-entry|rar-entry|unknown
    Lossless     bool
    BitrateKbps  int
    SampleRate   int
    BitDepth     int
    DurationSec  float64
    Confidence   float64       // уверенность сопоставления 0..1
    Source       string        // "file-list" | "site-tracklist" | "cue" | "sniff"
}
```

### 8.2 Пайплайн построения

```
buildIndex(mi *metainfo.MetaInfo, siteTracklist []SiteTrack, opts) (*Index, error)

1. files := mi.Info.UpvertedFiles()
2. audio := filter(files, isAudioExt)
3. if len(audio) > 1:
      // мультифайловый: сопоставляем по именам
      for each siteTrack: find best file by score() → TrackPlan{Source:"site-tracklist"}
      для файлов без соответствия — TrackPlan{Source:"file-list", Title=имя файла}
4. if len(audio) == 1:
      // однофайловый: sniff
      plan := sniffContainer(mi, audio[0])   // §5.3
      if plan.TrackCount > 1: раздать треки
      else: один трек = весь файл + сопоставить с siteTracklist по album/artist
5. Дополнительно: если в files есть .cue → cueIndex := parseCue(cue) → точные смещения
6. Сохранить Index в SQLite (key = infohash)
```

### 8.3 Sniffers (реализуемые модули)

| Модуль | Файл | Что извлекает | Требует данных |
|---|---|---|---|
| `sniff/flac` | `fLaC` | duration, sample rate, bit depth, VORBIS_COMMENT, CUESHEET, PICTURE | первые 64 КБ (+ хвост при CUESHEET) |
| `sniff/mpeg` | `ID3`/MPEG sync | ID3-теги (в т.ч. multi-track ID3), Xing/VBRI, длительность, битрейт | первые 64 КБ |
| `sniff/zip` | `PK` | список записей, CRC, offsets (EOCD + CD + LFH) | хвост 64 КБ + начало |
| `sniff/rar` | `Rar!` | записи файлов, packed/unpacked size, offsets, флаг solid | первые 256 КБ + последовательное чтение |
| `sniff/ogg` | `OggS` | кодек, rate, серийники страниц | первые 64 КБ |
| `sniff/wav` | `RIFF` | rate/bits/channels, длительность | первые 64 КБ |
| `sniff/mp4` | `ftyp` | `moov`/`mvhd` (duration), битрейт, `chpl` главы | хвост/начало |
| `sniff/ape` | `MAC ` | APEv2-теги, frames count | первые 64 КБ |
| `sniff/dsd` | `DSD ` | формат, sample rate, размер | первые 64 КБ |

Правила работы со «сниффами»:
- Каждый sniffer возвращает `[]TrackPlan` + уровень уверенности.
- Если sniffer требует данных с конца файла — приложение делает **точечный запрос** последнего piece'а (1 piece, а не весь файл).
- Любой sniffer должен корректно работать с «дырявыми» данными (piece'а в середине ещё нет) — sniff работает по мере поступления, с инкрементальным разбором.

### 8.4 Resync (для произвольного старта)

```
resyncMPEG(buf []byte) (offset int, ok bool):
  искать 0xFFE с корректным битовым паттерном (11 бит sync)
  проверить: version ∈ {1,2,3}, layer ≠ 0, bitrate index ≠ 15, samplerate index ≠ 3
  затем проверить цепочку 3–5 последовательных кадров с согласованной длиной
  → offset найден, можно декодировать (потеря ≤ 1 кадра)
```

```
resyncFLAC(buf []byte) (offset int, ok bool):
  искать заголовок фрейма FLAC: sync 0b11111111111110, block size bits, sample rate bits,
  затем проверить CRC-8 заголовка
  → смещение в samples можно уточнить по номеру кадра в заголовке
```

### 8.5 CUE sheet

```
REM GENRE ...
REM DATE 1998
REM COMMENT "..."
PERFORMER "Artist"
TITLE "Album"
FILE "Album.flac" WAVE
  TRACK 01 AUDIO
    TITLE "Song One"
    PERFORMER "Artist"
    INDEX 01 00:00:00
  TRACK 02 AUDIO
    TITLE "Song Two"
    INDEX 01 03:45:12
```

- `INDEX 01 mm:ss:ff` → sample offset = mm*60000 + ss*1000 + ff*sampleRate/1000.
- CUE-файл качается целиком (килобайты) и лежит в мультифайловом торренте → его файл известен из `info.files`, цена = 1 piece.

## 9. Проигрыватель и аудио-стек

### 9.1 Конвейер

```
PieceStore → TorrentFileReader (io.ReaderAt + Seek)
           → Decoder (FLAC | MP3 | FFmpeg)
           → PCM (f32le, 44.1/48/96/192 кГц)
           → Resampler (если частота устройства != частота файла)
           → Gain (ReplayGain, из тегов) + Fade in/out
           → Audio Device (beep: WASAPI / ALSA / Pulse / CoreAudio)
```

### 9.2 Декодеры

| Формат | Библиотека | Примечания |
|---|---|---|
| FLAC | `github.com/mewkiz/flac` (чистый Go) | lossless, поддержка 24/192, cue-разметка |
| MP3 | `github.com/hajimehoshi/go-mp3` (чистый Go) | CBR/VBR, gapless через Xing LAME-тег |
| WAV / AIFF | `github.com/mewkiz/wav`, `github.com/mewkiz/aiff` | |
| OGG Vorbis / Opus | `github.com/hraban/opus` / `ffmpeg` | Opus — только через ffmpeg |
| AAC / M4A / ALAC / APE / WavPack / DSD | внешний `ffmpeg` (subprocess, stdin→stdout) | fallback-универсал |

**Стратегия:** «чистый Go» для основных форматов (без внешних зависимостей), `ffmpeg` как fallback (ищем в PATH + стандартные места; если нет — понятное сообщение «формат требует ffmpeg»).

### 9.3 Буферизация и «первый звук»

- Размер буфера вперёд: по умолчанию 16 МБ (настраивается 8–256 МБ).
- Стратегия: после получения первого piece'а, содержащего начало трека, **начать декодирование немедленно**, не дожидаясь остальных; декодер стартует с resync.
- Плавный старт: 30 мс fade-in, чтобы не было щелчка.
- Индикация: `буфер: 12.4 МБ (74%)`, `TTFA: 2.8 с`.

### 9.4 Seek

```
seek(t):
  1. вычислить targetByte по карте контейнера:
       MP3 CBR: byte ≈ tagSize + t*bitrate/8
       MP3 VBR: по Xing TOC
       FLAC: по индексу фреймов (номер кадра в заголовке) либо по cue
  2. piece := targetByte / pieceLength
  3. запросить piece (+1 соседний) → дождаться
  4. resync → продолжить декодирование
  5. догрузить буфер вперёд
```

Latency seek: 0.5–3 с (зависит от скорости пира). Точность: ±1 фрейм (MP3 ~26 мс, FLAC ~1 сэмпл при точном индексе).

### 9.5 Gapless и альбомное воспроизведение

- Если треки идут из одного FLAC (album file) — используем межтрековые интервалы из cue.
- Если треки — отдельные файлы — используем LAME gapless-теги (MP3) или точную длительность (FLAC) + 20 мс crossfade-настройка (по умолчанию выключено, «без щелчка»).

### 9.6 Устройство вывода

`github.com/faiface/beep` — чистый Go, поддержка WASAPI (Windows), ALSA (Linux), PulseAudio, CoreAudio. Альтернатива: `github.com/ebitengine/oto` (cgo, шире охват, включая ALSA через cgo).

Параметры устройства: выбор устройства, громкость, «exclusive mode» (Windows) — для бит-перфектного lossless.

### 10.1 Схема SQLite (упрощённо, для наглядности)

```sql

  lossless INTEGER, samplerate INTEGER, bitdepth INTEGER
);

-- Торренты и раздачи
CREATE TABLE topic (
  id INTEGER PRIMARY KEY,     -- topic id на rutracker
  forum_id INTEGER, title TEXT, norm_title TEXT, mag_hash TEXT,
  size INTEGER, seeds INTEGER, peers INTEGER, rating REAL,
  dl_count INTEGER, created_at INTEGER, fetched_at INTEGER, raw_json TEXT
);
CREATE TABLE topic_tag (topic_id INTEGER, kind TEXT, value TEXT);  -- artist/album/genre/format/...

  id INTEGER PRIMARY KEY, info_hash TEXT UNIQUE, topic_id INTEGER,
  piece_length INTEGER, total_length INTEGER, num_pieces INTEGER,
  announce TEXT, created_at INTEGER
);
CREATE TABLE torrent_file (
  torrent_id INTEGER, idx INTEGER, path TEXT, offset INTEGER, length INTEGER,

);

-- Индекс треков внутри торрента (ключевая таблица)
```

## 11. Каталог, разделы и рекомендации

### 11.1 Разбор имени раздачи (нормализация)

Типовой формат: `[SOURCE] ARTIST - ALBUM - YEAR, FORMAT (tracks), QUALITY [SIZE]`

Примеры:
```
(Seychellois Séga, Seggae) [WEB] Phillip Toussaint - Monn Ganny Bless - 2026, FLAC (tracks), lossless [484.4 MB]
Madonna - The Immaculate Collection (2000) [FLAC] [Tracks]
Rammstein --complete discography- [FLAC]
```

Парсер выделяет:
- `source`: WEB / CD / Vinyl / SACD / Blu-ray / WEB-DL и т.п.
- `artist`, `album`, `year`
- `format`: FLAC / ALAC / APE / WV / MP3 / AAC / DSD
- `quality`: lossless / 24bit / Hi-Res / 320 / V0 / 128
- `tracks_marker`: `(tracks)` — **критический признак**: в раздаче отдельные файлы треков
- `collection_marker`: `discography`, `полная`, `collection`, `complete`, `studio`, `best of`
- `size`

Это даёт **быстрый предфильтр** ещё до скачивания `.torrent`: «это lossless с отдельными треками» → можно стримить.

### 11.2 Ранжирование lossless

```
qualityScore(раздача):
  DSD/DFF/DSF            → 100
  FLAC 24/96..192        → 95
  FLAC 16/44.1           → 90
  ALAC / APE / WavPack   → 88
  WAV                   → 85
  MP3 320                → 60
  MP3 V0 (≈245)          → 55
  MP3 V2 (≈190)          → 50
  MP3 128                → 30
  AAC 256                → 45
```

Правила выдачи:
1. По умолчанию — «lossless-only» переключатель **включён**.
2. Внутри одного исполнителя группируем по альбому и выбираем лучшую раздачу по `qualityScore`, затем по числу сидов, затем по рейтингу.
3. Бейдж «Lossless» / «24 bit» / «DSD» в UI.
4. Если lossless-раздача без сидов, а MP3-раздача с сидами — показываем оба, но по умолчанию выбираем lossless и честно предупреждаем: «сидеров нет, стрим может не начаться».

### 11.3 Агрегация «дискография исполнителя»

```
getArtistDiscography(artist):
  1. Найти все topic'ы по artist (разделы музыки) + отфильтровать по norm_name.
  2. Сгруппировать по (album, year) → выбрать лучшую раздачу.
  3. Отметить «коллекции» (одна раздача = вся дискография).
  4. Результат: список альбомов; каждый альбом → (topic, треклист, формат, сиды).
```

### 11.4 Рекомендации

| Источник сигнала | Алгоритм |
|---|---|
| Раздел | Новые раздачи раздела (RSS + tracker.php) |
| Похожие исполнители | Совпадение по жанру + «коллекции» + частота в одних компиляциях (лайб-паки) |
| Локальная история | Что слушал → исполнители → их альбомы; бонус за lossless |
| Смежные разделы | Рок ↔ Металл, Электроника ↔ Hi-Res |
| Треки в раздаче | «Ещё треки из этой раздачи» (тот же альбом) |

Реализация: скоринг + объяснение («похожие альбомы жанра Rock, lossless, 12 сидеров»). Без ML — только правила + локальная статистика.

## 12. Режимы хранения, SSD и лимиты трафика

### 12.1 Режимы

| Режим | Что пишется на диск | Когда использовать |
|---|---|---|
| `RAM` (по умолчанию для стрима) | Только в память (LRU, лимит 256 МБ) | Прослушивание; SSD не затрагивается вообще |
| `DiskCache` | Один sparse-файл на раздачу; куски, нужные для текущего трека | Если системе не хватает RAM или трек долгий/прерывистый |
| `Keep` | Полная загрузка выбранных треков/альбомов в отдельную папку | «Скачать трек/альбом/дискографию» |

### 12.2 Бюджет трафика

Настройки (по умолчанию):
- «Скачать максимум на трек»: без ограничений, но с **предупреждением** (FR-UX-3).
- «Лимит на сессию»: 2 ГБ.
- «Лимит на раздачу»: не докачивать остаток торрента автоматически (галочка выключена) → иначе ratio страдает.
- «Не скачивать трек целиком без подтверждения»: включено.

### 12.3 Про износ SSD (аргументация)

- Режим `RAM` → **0 байт** записи на SSD при стриминге.
- Режим `DiskCache` → запись только нужных piece'ов: трек 5 МБ → 5–6 МБ записи (а не 500 МБ скачивания + 500 МБ записи + 500 МБ удаления).
- Отсутствие операций «создать/удалить файл на 500 МБ» убирает главный источник износа (большие последовательные записи + erase-циклы).
- Один preallocated sparse-файл вместо тысяч мелких → меньше метаданных, меньше seek'ов.

Оценка (для SSD на 600 TBW, ~150 ГБ/год при 1 записи/день):
- Сценарий «50 треков в день по 6 МБ в режиме DiskCache» → 0.3 ГБ/день → ~110 ГБ/год → **≈0.2 % ресурса** (против ~2 ГБ/день при «качать и удалять» → 730 ГБ/год → ~1.2 %).
- В режиме `RAM` — 0 %.

### 13.1 Требования

|---|---|

| FR-NET-6 | Отсутствие DNS-утечек: резолвинг через SOCKS5 (`socks5h`) |
| FR-NET-7 | Никакого встроенного обхода DPI; приложение только «умеет ходить через прокси» |
| FR-NET-8 | Импорт/экспорт настроек прокси (например, из системных) |

### 13.2 Рекомендации по транспорту (информирование пользователя)

| Сценарий | Транспорт | Оценка |
|---|---|---|
| Форум доступен напрямую | Прямое соединение | Лучший случай |
| Форум заблокирован, есть VPN (WireGuard) | Весь трафик в VPN | Оптимально: P2P по UDP/TCP работает нормально |
| Есть SOCKS5-прокси | SOCKS5 для сайта и peer'ов | Хорошо, но UDP нет; для P2P нужен TCP-режим (µTP выкл) |
| Только Tor | Tor для сайта; peer'ы — напрямую | Работает, но медленно и рискованно для IP; предупреждать |
| DHT/PEX | — | Отключены (приватный трекер) — локализация трафика не требуется |

## 14. Приватность, безопасность, юридические аспекты

### 14.1 Безопасность

| Требование | Реализация |
|---|---|
| Секреты | `bb_session`, пароли, passkey — в системном хранилище (Windows DPAPI / libsecret / Keychain) либо в зашифрованном файле с ключом из ОС |
| Пароль | Не сохраняется; опционально — только хеш для локальной проверки |
| Телеметрия | Отсутствует. Никаких внешних серверов, кроме rutracker (и опционально fallback-источников) |
| Логи | Локальные, с ротацией; в логи **не пишутся** passkey, session-cookie и полные имена файлов? (имена файлов пишем — они нужны для отладки, но лог не покидает машину) |
| HTTPS | Весь HTTP-трафик к сайту — через TLS; проверка сертификатов без отключения (никакого InsecureSkipVerify) |
| Разбор HTML | Только через `goquery`; никакого выполнения скриптов страницы вне браузерного транспорта |
| Проверка целостности | Piece-хеши обязательны; данные, не прошедшие проверку, никогда не отдаются в декодер |
| Сторонние бинарники | `ffmpeg` запускается только из проверенного пути; аргументы не собираются из пользовательского ввода без экранирования |

### 14.2 Правовые аспекты (для заказчика)

- Приложение реализует протокол BitTorrent и клиент HTTP — это легальные инструменты (аналоги qBittorrent/Transmission/µTorrent).
- Ответственность за распространение и воспроизведение контента несёт пользователь. ТЗ не содержит средств обхода DRM и не содержит встроенного контента.
- Правила rutracker требуют поддерживать рейтинг раздачи; поэтому Ratio Guard — не «приятное дополнение», а часть корректной работы с площадкой.
- Для использования в стране пользователя может требоваться обход блокировок (применяется §13); ответственность за соблюдение законодательства — на пользователе.

### 15.2 Ключевые сценарии

**S1. Найти и послушать трек**
1. Раздел → фильтр lossless → список раздач (сортировка: рейтинг/сиды/новые).
2. Клик по раздаче → страница: треклист, формат, битрейт, сиды, «коллекция?», треки с длительностью.
3. Клик ▶ на треке → модальное подтверждение: «Скачаем ~6 МБ из 428 МБ (1.4 %). Начать?» (или без модалки, если выключено).
4. Плеер: буфер растёт, звук через 2–4 с. Индикатор «торрент-стрим».
5. «Докачать трек» — кнопка рядом с треком; скачивает только этот файл.

**S2. Скачать альбом**
Кнопка «⬇ Скачать альбом» → выбираются все файлы треков альбома (по подпапке/префиксу), piece-план считается → в очередь; режим хранения `Keep` → сохраняются с тегами (имя = `Artist - Album/01 - Title.flac`).

**S3. Скачать дискографию**
Страница исполнителя → «⬇ Скачать дискографию (lossless)» → приложение:
1. Находит все раздачи исполнителя (в т.ч. «коллекции» — одна раздача на всё).
2. Выбирает лучшие по qualityScore, дедуп по infohash, исключает дубли альбомов.
3. Формирует очередь с лимитом скорости и расписанием; показывает прогноз (объём, время, рейтинг).

**S4. Переключение треков в альбоме**
Клик по следующему треку → сессия та же, piece-план пересчитан, новый piece'ы запрошены → звук через 200–800 мс.

**S5. Оффлайн-библиотека**
Все скачанные треки появляются в разделе «Мои загрузки» с локальным воспроизведением.

## 19. Алгоритмы (детализация)

### 19.1 Расчёт piece-плана

```go
type PieceRange struct{ Start, End int } // включительно

func RangeForBytes(start, end, pieceLen int64) PieceRange {
    // end — исключительно
    s := int(start / pieceLen)
    e := int((end - 1) / pieceLen)
    return PieceRange{Start: s, End: e}
}

func ExtraBytes(start, end, pieceLen int64) int64 {
    s := start / pieceLen
    e := (end - 1) / pieceLen
    return (s+1)*pieceLen - start + end - e*pieceLen
}
```

### 19.2 Построение плана раздачи

```go
type Plan struct {
    FileIdx   int
    ByteStart int64
    ByteEnd   int64
    Pieces    PieceRange
    Extra     int64
}

func PlanForTrack(mi *metainfo.MetaInfo, fileIdx int) Plan
func PlanForAlbum(mi *metainfo.MetaInfo, files []int) []Plan
```

Для «альбома» piece-объединение: считаем объединённый диапазон piece'ов, но **важно**: скачиваем только piece'ы нужных файлов, а не «от первого до последнего» (иначе скачаются чужие треки между ними). Поэтому план — это **список** диапазонов, объединяемый только если они пересекаются.

### 19.3 Piece-picker (псевдокод)

```go
func (p *Picker) Next(ctx, want []bool, have []bool, peers []Peer) (piece int, ok bool) {
    candidates := []int{}
    for i := range want {
        if want[i] && !have[i] { candidates = append(candidates, i) }
    }
    if len(candidates) == 0 { return 0, false }
    if len(candidates) <= endgameThreshold { // 10
        return p.endgamePick(candidates, peers)
    }
    // rarest-first
    sort.Slice(candidates, func(i, j int) bool {
        return p.availability(candidates[i]) < p.availability(candidates[j])
    })
    return p.leastRecentlyServed(candidates), true
}
```

### 19.6 Оценка «сколько скачаем на трек» (для UI)

```go
func EstimateDownload(mi, fileIdx) (bytes int64, pieces int, extra int64) {
    f := mi.Info.UpvertedFiles()[fileIdx]
    pr := RangeForBytes(f.Offset, f.Offset+f.Length, mi.Info.PieceLength)
    bytes = int64(pr.End-pr.Start+1) * mi.Info.PieceLength
    extra = ExtraBytes(f.Offset, f.Offset+f.Length, mi.Info.PieceLength)
    return bytes, pr.End - pr.Start + 1, extra
}
```

### 23.2 Гибридный режим (рекомендуется)

```
Выбран трек
  │
  ├─ 1. Есть локальная копия (скачанный ранее)          → локальное воспроизведение
  ├─ 2. Есть активная lossless-раздача с сидами          → P2P-стрим (основной путь)
  ├─ 3. Раздача есть, но 0 сидеров / трек не найден      → предложить «быстрый источник»:
  │        • SoundCloud (128, полный трек, официальный API)
  │        • Bandcamp (128, официальная покупка = lossless)
  │        • Deezer preview (30 c, мгновенно)
  │        → с пометкой в UI: «поток 128 kbps, lossless-версия недоступна»
  └─ 4. Раздачи нет вообще                               → поиск по каталогу rutracker
```

**Почему гибрид лучше чистого P2P:**
- P2P даёт **качество** (lossless) и **полноту** (дискографии) — то, ради чего всё затевалось.
- Fallback даёт **доступность** (не зависит от наличия сидеров) — убирает главный UX-риск.
- Метаданные (Last.fm/MusicBrainz) дают **каталог** и **обложки** без парсинга форума.

### 23.3 Вариант «только внешние источники» (если P2P-часть отклонена)

Если по результатам Phase 0 выяснится, что announce заблокирован (R-1) или пользователь не хочет P2P:

> 📄 **Отдельный документ:** `ТЗ_RutStream_Lite_без_P2P.md` — подробное ТЗ варианта «без P2P» (каталог + плеер на SoundCloud/Bandcamp/Deezer/iTunes/MusicBrainz) с проверенными контрактами API, планом на 6–12 дней и инструкцией, как встроить P2P-адаптер в этот код без переписывания UI.

**Реализуемый минимум:** приложение = каталог + плеер с 3–4 источниками.

| Источник | Что реализовывать | Сложность |
|---|---|---|
| SoundCloud | OAuth client_id (официальный API), поиск, `GET /tracks/{id}/stream` → HLS/прямой MP3 | 2–4 дня |
| Bandcamp | Парсинг страницы трека/альбома: извлечение `mp3-128`/`mp3-320` URL в JSON-врезке; превью 30 с; покупка lossless | 2–3 дня |
| Deezer | Поиск + `preview` URL (30 с) | 0.5 дня |
| MusicBrainz/Last.fm | Метаданные, обложки, теги | 1–2 дня |

**Оценка:** 6–10 дней вместо 37–51. **Потеря:** lossless и полные дискографии (то есть ~80 % исходной ценности задачи). **Плюс:** не нужен BT-движок, нет рейтинга/приватного трекера, нет CF-проблем для трекера, проще юридически.

**Рекомендация:** гибрид. Сначала Phase 0 + Phase 1 (P2P — ядро ценности), затем отдельный модуль fallback-источников как «Phase 2.5» (2–3 дня на SoundCloud + Deezer).

### 23.4 Что точно НЕ стоит делать

| Идея | Почему |
|---|---|
| Свой DHT/ трекер | Приватный трекер, DHT запрещён, бессмысленно |
| Скачивать целиком и «стримить с диска» | Проблема, которую как раз решаем (износ SSD) |
| Свой распаковщик RAR solid | Требует полного архива; экономия не окупает сложность |
| Распознавание музыки по спектру (Shazam-подобное) | Дорого, ненадёжно, не нужно при наличии треклистов |
| Собственный облачный кэш | Юридически и финансово нецелесообразно |

## Приложение G. Итоговое резюме для заказчика

1. **Задача реализуема.** Способ «найти трек в полной дискографии, не скачивая её» найден и описан: список файлов уже содержится в `.torrent` (80–90 % раздач), а для однофайловых раздач применяется построение индекса по заголовкам контейнера (FLAC/MP3/ZIP/RAR) с докачкой 1–2 piece'ов вместо 500 МБ. Дополнительно, rutracker сам отдаёт список файлов раздачи через `viewtorrent.php` — то есть треклист известен ещё до скачивания данных.
2. **Основной риск — не алгоритмы, а доступ к трекеру**: announce-сервер rutracker находится за Cloudflare, и в ходе разведки вернул 403. Phase 0 (3–5 дней) существует именно для проверки этого; если проблема окажется неустранимой, §23.3 описывает реализуемую альтернативу (SoundCloud/Bandcamp/Deezer) ценой отказа от lossless-дискографий.
3. **Потоковый режим решает проблему SSD**: вместо «500 МБ скачать → послушать → удалить» скачивается 1–5 % от раздачи на трек; в режиме RAM — 0 байт записи на диск.
4. **Рейтинг (ratio) — обязательное требование**, а не опция: приложение должно раздавать скачанное и уметь до-качать остаток раздачи в фоне.
5. **Оценка:** 37–51 рабочий день для полного решения, 3–5 дней до точки принятия решения (Go/No-Go).
